# `gateway` — Mode A on `:5033`

The HTTP surface the web UI (and anything else) talks to, and the process that *is* the
tutor. IDEA.md *The fork* defines Mode A as "gateway runs the same prompt pack through
`llm-svc`"; this is that process.

Per CONTRACTS.md's stack decision it holds four things in one process — the gateway routes,
`llm`, `tutor` and `corpus` — each a router that can be lifted out later. Only two things
are over the network: `learner-svc` (the one stateful service, its own volume) and
`render-svc` (the one Node service).

```
web-ui ──► learn-gateway :5033 ──► learner-svc :5034   (HTTP, every durable fact)
              │  llm      (in-process, /api/llm/*)
              │  corpus   (in-process, /api/corpus/*)
              │  tutor    (in-process, decisions + the prompt pack)
              └────────► render-svc :5035  (HTTP, optional)
```

Spec: [`IDEA.md`](../../IDEA.md). Binding shapes: [`CONTRACTS.md`](../../CONTRACTS.md) —
*Gateway HTTP (Stage 2)* and *Gateway response shapes*. The decision rules:
[`tutor.md`](tutor.md). The service it writes through: [`learner-svc.md`](learner-svc.md).

## What is decided by code, and what is generated by a model

This is the line the whole module is arranged around.

| Decided by `tutor/orchestrator.py` (code) | Generated by the model through the prompt pack |
|---|---|
| Which node comes next (via learner-svc's selection) | The question on that node |
| Whether an answer is correct — key match, server-side | The wording of the feedback |
| Whether a hint level is allowed | The text of the hint at that level |
| Which strategy to teach with | The explanation in that strategy |
| Whether a teach-back is due | The teach-back score against the frozen rubric |
| The misconception step order, and confirm-vs-drop rules | Whether one free-text reply *is* the belief |
| When the session ends | The session log's prose |
| The feasibility arithmetic | The plan graph's nodes and edges |

And a third column that is neither: **learner-svc recomputes every number.** The gateway
holds no learner model, no mastery estimate and no counters about the learner. What it
persists is a phase and a set of answer keys.

## The phase machine

`grounding → plan → probe → teach → done`, per goal, in `LT_DATA_DIR/gateway/state.json`.

| Phase | Set by | Meaning |
|---|---|---|
| `grounding` | `POST /api/goals` | The goal exists; sources and research may be added |
| `plan` | `POST /api/goals/{g}/plan` | A graph exists and is **waiting for the learner's review** |
| `probe` | `POST /api/goals/{g}/plan/approve` | The graph is approved; the probe may run |
| `teach` | the probe's stop rule firing, or `POST .../session/start` | Teaching |
| `done` | `teach/next` finding nothing left | Every node is known |

It is persisted because CONTRACTS.md returns `phase` on three routes and it is not
derivable from learner-svc: a goal with a graph and no probe events could be mid-review or
mid-probe, and those are different states. `POST /api/goals/{g}/probe/start` refuses with
`400 plan_not_approved` on an unreviewed graph — plan.md: "Do not start the probe on an
unreviewed graph."

## The answer keys never leave the gateway

`learner next` deliberately serves a stem and options and **not** the key. So the gateway
stores the key when it authors the item (`state.json`, `questions[item_id]`) and grades
against it. `ProbeAnswerIn` and `TeachAnswerIn` both *accept* a `correct` field, because
the contract's body shape has one — and it is never read. A client that posts
`{"response": "A", "correct": true}` against a key of `B` gets `correct: false` back and a
`0` in the event table. `tests/test_gateway_routes.py::test_the_server_side_key_decides_not_the_client`
pins it.

An answer for an item the gateway has no key for is **409 `unknown_item`**, not a guess.

## Interrupts — "wait, why?" mid-step

`POST /api/goals/{g}/teach/interrupt` `{session_id, node_id, question}` →
`{answer_markdown, citations[], step_unchanged: true, refused_checkpoint_answer: bool}`.

SKILL.md *Interrupts and disputes*: "answer inline in ≤ 5 lines, add no new node, then
resume the **same** step from where it stopped." So the route is deliberately inert. It:

- **does not advance the step** — nothing is regenerated, and the step markdown the gateway
  already served is passed *into* the prompt as the context being asked about, so the answer
  is about the step on the learner's screen rather than a second, unseen one;
- **does not touch the assistance level**, the attempt count or the in-flight item;
- **writes no evidence** — no `POST /v1/events`, no misconception, no session log entry.

`step_unchanged: true` is on every response, refusal included: it is the client's licence to
keep rendering the step it already has.

**It refuses the reveal by another route.** An interrupt that is really "which option is
correct?" would be a level-6 hint before an attempt (CONTRACTS.md hard rule 1). So
`tutor.orchestrator.asks_for_the_checkpoint_answer` runs **before any generation**, and a
match returns `checkpoint.md`'s hint-ladder rule text with `refused_checkpoint_answer: true`.
The refusal is fixed text from code, not a model asked politely to decline — a model asked to
refuse can be negotiated with. It fires only while a checkpoint is actually in flight.

**Citations, or an abstention that is visible.** `cite_or_abstain` runs on the answer's
leading sentence (a whole answer as the claim abstains by length alone — the scorer measures
the fraction of a claim's content words present in a chunk). With no citation the note goes
**into the markdown**:
*"No source found for this — there are no sources on this goal. Answered from model knowledge,
not from your material."* An empty `citations` list on its own would let the UI show an
uncited answer as if it were sourced.

**Nothing durable is recorded, and that is a gap, not a choice.** learner-svc has no note
route: `POST /v1/events` accepts `answer` and `teach_back` only, and `POST /v1/sessions/{s}/log`
writes the whole md-log at session end. A `note` event kind exists in the learner core but
only `learner log` writes it. So the interrupt is appended to the gateway's own
`teach.steps` as `{kind: "interrupt", question, refused_checkpoint_answer}` — visible in
`state.json` and in the passport, not in the event table, and it does **not** appear in the
session log (`session-log.md`'s section list is closed, and the log is a study artifact, not
a transcript). If interrupts should be durable, the change is a note route on learner-svc,
not a second writer here.

409s: `not_teaching` (the goal is not in the teach phase), `wrong_session` (a session other
than the open one), `not_current_node` (any node but the one being taught — the gateway will
not re-teach a past node to answer a question about it).

## Holdouts

`GET /api/goals/{g}/holdouts/due` and `POST /api/goals/{g}/holdouts/answer`
(CONTRACTS.md *Gateway response shapes — holdouts*), in `routes/holdouts.py`, plus the
auto-promote rule in `tutor/orchestrator.py::promote_if_due`, called from `teach/answer`.

**Why they exist.** The three gate numbers in `learner/metrics.py` — 7-day holdout success,
false-mastery, item rejection — are computed on holdout checks and nothing else, and a
holdout is a flag drawn at *promotion* (`items.promote` → `assign_holdout`). The gateway
authored items, validated them with the blind solver, recorded answers on them, and never
once called `POST /v1/items/{i}/promote`; and it had no route that served a holdout. So the
product could run for months with `holdout_success_7d.rate_percent: null`. The CLI and MCP
could do both (`learner item promote`, `learner holdout-check`), the product could not.

**The rule, and who owns what.** After a checkpoint is recorded, the gateway reads the
item's uses from learner-svc — `GET /v1/events?node=…`, rows of kind `answer`/`probe_answer`
whose `payload.item_id` (or `item_version_id`) is this item — and when
`uses >= LT_PROMOTE_MIN_USES` (default 3; `Settings.promote_min_uses`, the same variable
learner-svc's own `items.promote` reads) and the item is `PRACTICE_EVIDENCE`, it posts
`/v1/items/{i}/promote` with the request's `Idempotency-Key` scoped `:promote`. It reads
learner-svc's rows rather than keeping a counter of its own so that a replayed answer
(same key, same body) counts once, like the event it replayed. learner-svc keeps the full
promotion rule — validated, enough uses, at least one correct, not all IDK, no open
ambiguity dispute — and makes the holdout draw; its 400 comes back in the answer's
`promotion.reason`, never as an error, because the checkpoint was recorded either way.
`teach/answer` gains `promotion: {attempted, promoted, status, holdout, uses, min_uses,
reason}`. `status` is what learner-svc said the item is; `holdout` is its draw (`null` when
nothing was attempted).

**The two routes.** `due` is a proxy of `GET /v1/holdouts/{g}/due` with each pick shaped
as the contract's `Question` (no key) plus `context` (`transfer` when the item version has
a `surface_form`, `delayed` otherwise), learner-svc's `reason`, and `key_on_file` — `false`
for a holdout promoted through the CLI or MCP, which the gateway can list but not grade.
`answer` grades against the stored key (409 `unknown_item` otherwise), records through
`POST /v1/events` with the given `context` and assistance 0, and returns `{correct,
context, recorded, node_state, counts_toward_mastery}`. `context` must be `delayed` or
`transfer`; `in-session` is a 400 here — that is what `teach/answer` is for.

**What they do not do.** No phase change: a holdout is checkable in any phase past `plan`
and the phase machine is not read or written. No in-flight item, no hint ladder (a holdout
answered with help would flatter exactly the number it exists to measure), no feedback,
no step, no model call. learner-svc's `next` still never serves a holdout in any mode;
`tests/test_gateway_holdouts.py` re-asserts that across all four modes after forcing one.

`tests/test_gateway_holdouts.py` pins this against the in-process learner-svc: the third
checkpoint answer promotes and the first two do not (item status read back from `items`);
a forced holdout appears in `due` and disappears after the answer; a `transfer` answer
posted twice with the same `Idempotency-Key` writes one row; and
`GET /api/goals/{g}/metrics` then reports one holdout check with one pass, and one node
with holdout checks in `false_mastery` — a non-zero denominator for the gate numbers.

**Known limitations.** Nothing schedules the check: the due list has to be asked for
(the web UI and the Telegram job do not call it yet). `due` is per goal only, like
learner-svc's route. A holdout the gateway did not author cannot be answered here.

## Feasibility on the plan response

`POST /api/goals/{g}/plan` returns `feasibility` — the orchestrator's arithmetic
(`nodes_remaining × PACE_MIN` vs `minutes_per_session × sessions_left`, see
[tutor.md](tutor.md)) — carrying **web-ui's field names alongside its own**:

| Key | Meaning |
|---|---|
| `sessions_needed` | `ceil(minutes_needed / minutes_per_session)`, minimum 1 |
| `sessions_available` | `sessions_left` under the UI's name; `null` with no deadline |
| `verdict` | `comfortable` (≥ 1.25× needed) · `tight` (≥ needed) · `not-feasible` · `unknown` |
| `assumption` | The one line printed under the sentence: concepts left, PACE_MIN, minutes per session — and that it is an estimate |

`web-ui/src/lib/types.ts::Feasibility` is `{sessions_needed, sessions_available, verdict,
assumption}` and `PlanPanel` reads exactly those four. Before this the gateway sent only its
own names, so the UI's `feasibility.verdict` was `undefined` and its sentence rendered
`undefined sessions left`. **The UI's names won**; nothing was renamed away, so
`statement`, `options`, `fits` and the rest of the arithmetic are still there for the docs,
the tests and `state.json`. The 1.25× threshold is copied from `src/lib/feasibility.ts` so the
gateway's line and the UI's own fallback cannot disagree about the colour of the same numbers.

Two things to know about the numbers themselves: the gateway budgets `PACE_MIN` = **12**
min/node and the UI's fallback budgets **20**, so the gateway's `sessions_needed` is the
lower of the two — the gateway's wins when it is sent, and both print their assumption.
And `feasibility` is **`null`** when `minutes_per_session` is 0: with no session length there
is nothing to divide by, and a null lets the UI fall back to its own estimate instead of
rendering empty numbers. A goal with a session length but no deadline still gets an object,
with `sessions_available: null` and `verdict: "unknown"`.

## Routes

Every route in CONTRACTS.md's *Gateway response shapes*, at the path and with the keys it
names. Extra keys are additive; nothing contracted is renamed or missing.

| Verb + path | Notes |
|---|---|
| `POST /api/goals` | `goal_id` optional — slugified from `title` when omitted. The five contract-only fields (`concept`, `sessions_per_week`, `target_capabilities`, `transfer_required`, `domain`) live in gateway state and are merged onto every goal read |
| `GET /api/goals` | Adds `phase`, `node_count` and the four colour counts per goal |
| `GET /api/goals/{g}` | `session` is the open session or `null`; `summary_md` is learner-svc's markdown verbatim |
| `POST /api/goals/{g}/sources` | multipart `file` (repeatable) + `role`; writes into `LT_DATA_DIR/sources/<goal>/` and ingests |
| `GET /api/goals/{g}/sources` | plus `sources_md_fields`, the parsed `sources.md` |
| `POST /api/goals/{g}/research` → `.../approve` | Proposes and records. **No web access** — corpus.md puts the browsing half in an agent host with a real search tool, because that is where invented sources enter |
| `POST /api/goals/{g}/plan` | Corpus structure in as a prior, `cite_or_abstain` out as `verification`. Also returns `feasibility` (or `null` — see *Feasibility on the plan response*), `dropped_edges` (edges the model pointed at nodes it never declared) and the four `review_questions` from plan.md. `warnings` appears only when the graph is still under `LT_PLAN_MIN_NODES` after one retry |
| `POST /api/goals/{g}/plan/approve` | The learner's one manual review. `ops` are applied through `graph revise` |
| `POST /api/goals/{g}/probe/start` \| `/answer` | 409 on an unknown item; `stop_reason` names which of probe.md's rules fired |
| `POST /api/goals/{g}/teach/next` | 409 `nothing_to_teach` when the graph is exhausted (and the phase goes to `done`) |
| `POST /api/goals/{g}/teach/interrupt` | "Wait, why?" mid-step. Answers against the step already served and moves nothing — see *Interrupts* above. 409 `not_teaching` / `wrong_session` / `not_current_node` |
| `POST /api/goals/{g}/teach/hint` | 409 `hint_refused` for the reveal before an attempt, and for a skipped level |
| `POST /api/goals/{g}/teach/answer` | `decision` is the orchestrator's; `misconception_suspected` names the distractor's belief |
| `POST /api/goals/{g}/teach/teach-back` | `rubric_version` comes from the rubric file; adds the rubric's `action` for that score |
| `POST /api/goals/{g}/misconception/step` | `outcome` may be supplied by the caller; otherwise the model judges it and the reply comes back too |
| `POST /api/goals/{g}/dispute` | "I already know this" comes back with two authored check items |
| `POST /api/goals/{g}/session/end` | Composes the md-log, `POST`s it to `/v1/sessions/{s}/log`, returns learner-svc's `log_path` |
| `POST /api/goals/{g}/session/start` | **Not in the contract.** A returning learner past the probe needs a door into a session; `probe/start` is the contracted one |
| `GET /api/goals/{g}/map` | Curriculum (learner-svc's mermaid) and path (a straight line, coloured) |
| `GET /api/goals/{g}/receipts/{node}` | Four learner-svc reads: the graph, `/v1/events`, `/v1/misconceptions`, `/v1/disputes`. `why` is learner-svc's own `reasons` list |
| `GET /api/goals/{g}/metrics` | Straight passthrough |
| `GET /api/passport` | `application/zip` — see below |
| `POST /api/render` | `/check` first, so a diagram that will not parse is a 400 here rather than a broken SVG downstream |
| `GET /api/health` | All four dependencies |
| `/api/llm/*`, `/api/corpus/*` | The two mounted routers, unchanged |

### Errors

Always `{"error": "...", "code": "..."}`.

| Status | When |
|---|---|
| 400 | A rejected request, ours or learner-svc's (passed through verbatim) |
| 404 | An unknown goal, node or item |
| 409 | A refused hint, an idempotency conflict, an item with no stored key, nothing left to teach, an interrupt aimed at a step that is not on screen (`not_teaching`, `wrong_session`, `not_current_node`) |
| 502 | learner-svc down, render-svc down or unconfigured |

### `Idempotency-Key`

Passed through to learner-svc, which owns the replay table. One client key fans out to
several learner-svc writes on some routes (a session **and** an item on `probe/start`), so
each write gets the key with a suffix — `plan-1:session`, `plan-1:item:n_…` — because the
replay table keys on `(key, body-hash)` and one key against two different bodies is a 409
by design.

## Health

`GET /api/health` returns `ok`, `services` (`learner`, `render`, `llm`, `corpus`, each
`ok` / `unconfigured` / `degraded` / `down`) and a `detail` map. `detail.llm` carries `provider`,
`model`, `solver_provider`, `solver_model`, `solver_differs_from_tutor`, and — when a role
runs on ollama — `model_present` / `solver_present`, read from one `GET ${OLLAMA_URL}/api/tags`
(2 s timeout, never raises). `true`/`false` means Ollama answered; `null` means the role is
not ollama or Ollama could not be reached, in which case `error` says why. A model that is
configured but not pulled makes `llm` report `unconfigured`, and an unreachable Ollama makes
it report `degraded`. `ok` is `true` unless a service is `down`: the gateway and its
model-free study tools still work while the model is missing or unreachable.

## The passport zip

`GET /api/passport` is **learner-svc's zip, wrapped**. The gateway fetches
`GET /v1/passport` — `events.jsonl`, `state.json`, `learner.md`, `notes.md`, `goals.json`,
`graph.json`, `disputes.json` and the vault's session logs under `artifacts/sessions/` —
copies every member across, and adds the two things learner-svc cannot know about:

| Added member | What it is |
|---|---|
| `gateway-state.json` | The phase machine and the answer keys, from `LT_DATA_DIR/gateway/state.json` |
| `artifacts/*.svg` | Rendered diagrams, if any. **Nothing writes them today** — `teach/next` returns the SVG inline and does not persist it — so this is normally empty |

`MANIFEST.json` is the gateway's, with learner-svc's own manifest kept verbatim under
`learner_svc`, so a reader can see which process produced each member.

Wrapping rather than re-assembling is the point of the change: the service that owns the
volume builds every member in one read of its own database. A learner-svc that is down is
now a **502**, not a passport that is quietly missing its events — which is what the old
direct-read fallback produced whenever the two did not share a filesystem.

## Deviations from CONTRACTS.md

| Deviation | Why |
|---|---|
| **`recorded` is learner-svc's write receipt plus the columns of the row it wrote.** CONTRACTS.md says `recorded: Event` | learner-svc returns `{event_id, item_status, counts_toward_mastery, node_state, …}` — a receipt, not the event row, and it has no route to read the row back. The gateway adds the fields it posted (`kind`, `response`, `correct`, `confidence`, `assistance_level`, `context`, `prompt_version`, `grader_version`) so the caller gets the `Event` the contract names. Nothing is recomputed and no learner-svc key is dropped |
| **`edges` use `from_node`/`to_node`** | That is learner-svc's `Edge` shape, and the contract says `NodeState = learner-svc node state`. Passing it through beats a second definition that can drift |
| **Hints below level 6 do not require a prior attempt** | The contract says "level ≤5; 6 only after an attempt → 409 otherwise" and the web UI is coded to it. `checkpoint.md` is stricter. See [tutor.md](tutor.md) *Deviations* — changing this means changing CONTRACTS.md first |
| **`POST /api/goals/{g}/session/start` is an extra route** | A returning learner whose probe is finished otherwise has no way to open a session |

Two deviations that used to be in this table are closed rather than documented again.
`GET /api/goals/{g}/receipts/{node}` and `GET /api/passport` read
`events.db` directly, and the session md-log was written into the vault by the gateway,
because learner-svc had no routes for any of it. It now does — `GET /v1/events`,
`/v1/disputes`, `/v1/misconceptions`, `/v1/passport` and `POST /v1/sessions/{s}/log`
([learner-svc.md](learner-svc.md) *The five Stage 2 additions*). `DirectLearnerReads` and
the `LT_LEARNER_DIRECT_READS` flag are deleted; `LearnerClient` and `RenderClient` are the
only two ways out of this process, and
`tests/test_gateway_routes.py::test_receipts_and_the_passport_have_no_second_path_into_the_database`
pins that by pointing the gateway at a refused connection and asserting 502 on both.

## Known limitations

* **One writer.** The state file is whole-file replaced under a lock. One gateway process
  per data directory; two would race on `state.json` (and on SQLite behind learner-svc,
  which has the same limitation).
* **Losing `state.json` loses the session in flight.** The answer keys for questions
  already served go with it, so those answers become 409s. No evidence is lost — evidence
  is learner-svc's. The file is a cache with a phase in it, not a second learner model.
* **The keys grow without bound.** `questions` is never pruned; one entry per item ever
  authored for that goal. At personal-tool volumes that is kilobytes, and there is no
  sweeper.
* **No authentication, no CORS policy.** Same posture as learner-svc: bind `127.0.0.1` and
  put it behind something if it ever leaves the machine. Anything that can reach the
  gateway can teach as, and rewrite, the learner.
* **A slow model still blocks the request.** `LT_LLM_TIMEOUT_S` (default 120) is the
  timeout on every provider call ([llm.md](llm.md)). A 12B local model (`gemma3:12b`) on a
  plan-sized prompt exceeded 60 s every time, which is why the default is 120 s;
  `llama3.1:8b` with `LT_LLM_MAX_TOKENS=2000` completed the same call in about 21 s.
  Raising the ceiling does not make the model faster — it means a slow plan finishes
  instead of failing, at the cost of a request that can hold a worker for two minutes.
* **Every LLM call is blocking and uncached-per-request.** `generate_structured` runs
  `asyncio.run` internally, so the routes are sync (FastAPI runs them in a threadpool). A
  `teach/next` is three model calls plus two render calls in series; on a local 12B model
  that is tens of seconds. No streaming anywhere.
* **`GET /api/goals` is O(goals) round-trips** — one graph read per goal to count the
  colours.
* **The research route does no research.** By design (corpus.md), but it means the
  grounding phase is only half a phase without an agent host driving the web half.
* **The web-ui mount is a static export only.** `LT_WEB_DIR` is served by `StaticFiles`;
  a Next.js server-rendered app needs its own container and a reverse proxy.

## Run against a local model

The stack has been run end to end on one machine with Ollama: `learner-svc` and
`learn-gateway` on a temporary `LT_DATA_DIR`, tutor `llama3.1:8b`, solver `gemma3:12b`,
`LT_LLM_MAX_TOKENS=2000`, and `LT_RENDER_URL` unset. What that exercised, and what it
showed:

* `GET /api/health` reports `learner`, `llm` and `corpus` as `ok`, `render` as
  `unconfigured`, and `solver_differs_from_tutor: true`.
* A new goal, a small corpus ingest and one real `POST /api/goals/{g}/plan` return a typed
  graph (strict prerequisites, a course-sequence edge, a transfer edge) built with the
  corpus structure as a prior, a `verification` list that mixes `cited` and `abstain`
  rows, and the feasibility sentence. With these settings the plan call takes about 21 s.
* With a graph, an item and an answer written through learner-svc directly (no model),
  receipts, `session/end` and the passport are all served from learner-svc's HTTP routes:
  the receipts come from the four reads listed under *Routes*, the session log is written
  into the vault by learner-svc together with its `note` event, and the passport zip
  carries the members listed in *The passport zip*. learner-svc is the only process that
  opens the database.
* A small local model follows the shape of the plan pack but not its size: `llama3.1:8b`
  returned 5 nodes where `plan.md` asks for 10–40. That is what `LT_PLAN_MIN_NODES` is for:
  a plan under the floor is retried once with the count stated, and if it is still short
  the gateway returns it with `warnings: ["plan has 5 nodes; plan.md asks for 10–40"]`
  rather than pretending. See [tutor.md](tutor.md) *Known limitations*.

One Windows note: a `learner-svc.exe` or `learn-gateway.exe` that is still running holds a
lock on `.venv/Scripts/*.exe`, and `uv sync` then fails with `os error 32`. Stop both
servers before the next `uv sync`.

## Tests

```bash
uv run pytest -o addopts="" -q tests/test_gateway_routes.py
```

40 tests. learner-svc is mounted **in-process** — its real `create_app`, reached through a
synchronous httpx transport backed by `TestClient` — so every event the flow writes lands
in a real SQLite event table and every state it reads was recomputed by the real evidence
rules. Only the model is faked (`FakeLLM`, canned Pydantic objects per schema) and
render-svc is an `httpx.MockTransport`. `test_full_flow` runs goal → ingest → plan →
approve → probe ×3 → teach → refused reveal → wrong-at-high-confidence → misconception
step → hint → right → teach-back → session end → map → receipts → passport → health in one
pass. Two tests pin the gateway's reliance on learner-svc's HTTP surface: receipts and the
passport are 502 when learner-svc is unreachable (no second path into the database), and
the session log is the file learner-svc wrote, with the `note` event `learner log` appends.
